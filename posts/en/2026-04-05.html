My Third Server: Going All-In on Containers

April 5th, 2026

Third time's the charm

Every self-hoster has a story about how they got started. Mine begins with an $80 computer someone threw away. I pulled it out of a pile of e-waste, slapped Linux on it, and somehow got Minecraft and a MySQL server running. It worked! Sort of. I had no idea what I was doing, and honestly that was half the fun.

My second attempt was the one I wrote about previously. A $200 Intel N100 mini PC where I learned what I was doing. I figured out systemd, got a dedicated reverse proxy running, and kept a growing list of services humming along on 16GB of RAM. That little box punched way above its weight. But over time I kept running into the same friction: every service was installed directly on the host, tangled together, fighting over dependencies. Updating one thing risked breaking another. It was fragile in ways that only became obvious at the worst possible moments.

So I did what any reasonable person would do. I bought a much beefier computer.

The new machine

beefier Meet the Framework Desktop, packing an AMD Ryzen AI Max 300 series processor, 128GB of RAM, and an 8TB SSD. Coming from 16GB and a 512GB drive, this feels absurd. It's a real workstation, not a toaster-sized mini PC. Framework's whole pitch is repairability and upgradability, which aligns perfectly with the self-hosting ethos: you own the hardware, you control it, and you can fix it yourself rather than throwing it away when something breaks.

The Ryzen AI Max also happens to have a capable integrated GPU. Running local LLMs at full speed and handling video transcoding in Jellyfin without breaking a sweat are now both legitimately viable. The hardware headroom is finally there. But the real upgrade wasn't the specs. It was the decision to do everything differently this time.

What are containers, anyway?

On my second server, every service I ran was installed directly onto the host system. All of them lived in /usr/ or /etc/, sharing the same libraries, the same filesystem, the same fate if something went wrong. This works fine until it doesn't. Software A needs Python 3.9, Software B needs Python 3.12, and suddenly you're in dependency hell.

Containers solve this by wrapping each application in its own isolated box. Think of it like shipping containers on a cargo ship: the ship doesn't care what's inside each container, and the contents of one container can't spill into another. Each service brings exactly what it needs to run: its own libraries, its own configuration, its own little slice of the filesystem. Nothing else on the host can interfere with it.

The most popular container tool is Docker, but I went with Podman. The two are nearly identical from a usage standpoint, but Podman has a philosophy I find more appealing: it's daemonless. Docker runs a persistent background daemon with root privileges that manages all your containers. Podman doesn't. Each container is simply a process, and importantly, you can run them entirely as a regular user with no root involvement at all.

Running everything in user space

That last point deserves its own section because it's the architectural decision I'm most happy about. With one exception for system-level services, every single container on this machine runs in what's called "user space," meaning Podman starts them as my regular user account, not as root.

Why does this matter? Security, mostly. If a container is ever compromised, the blast radius is limited to what my user account can do. There's no path to owning the whole machine through an exploit in, say, a poorly configured Nextcloud plugin. On my previous server, most services ran with elevated privileges because that's how things were installed. It worked, but it was laziness masquerading as a setup.

Podman in user space also integrates cleanly with systemd through quadlet, a way of defining containers as simple .container files that systemd understands natively. Instead of a giant docker-compose.yml, each service gets a small declarative file that describes what image to run, what ports to expose, and what volumes to mount. Systemd takes it from there: starting containers on boot, restarting them on failure, managing startup order. It's the best of both worlds: the isolation of containers with the reliability of systemd.

What's running on it

The service list has grown considerably since my N100 days. On the media side, Jellyfin handles my movie and TV library, with Sonarr, Radarr, Bazarr, and Prowlarr forming the usual automated pipeline around it. qBittorrent runs behind Gluetun so all its traffic goes through a VPN, a small detail that matters a lot when you care about what leaves your network.

For personal cloud stuff, Nextcloud replaces Google Drive, Immich replaces Google Photos, and Gitea is my private GitHub. All of them backed by a shared Postgres database and Redis instance. These used to feel like ambitious services to self-host; now they're merely entries in a container file that start themselves.

The addition I'm most excited about is the local AI stack. Ollama runs full-size language models using the integrated GPU, and Open WebUI sits in front of it as the chat interface. I wrote about wanting to do this on the N100, where it wasn't really feasible. With 128GB of unified memory and a proper GPU, large models run fast enough to practically use. My data never touches OpenAI's servers. For the paranoid self-hoster, this is the dream.

Networking is handled by Nginx Proxy Manager as the reverse proxy, Cloudflare tunnels for exposing services to the internet without opening ports, and AdGuard Home for network-wide DNS ad blocking. Tailscale and Cockpit are the only two things that run directly on the host rather than in containers: Tailscale because it's a VPN that needs deep network access, and Cockpit because it's a web dashboard for administering the machine itself. Everything else: containerized.

What I learned from doing this three times

The first time around I was simply following tutorials and hoping for the best. The second time I understood what I was building but made peace with a lot of technical debt. This time I stopped and asked: if I had to rebuild everything from scratch, how would I do it? The answer was containers, and I rebuilt accordingly.

The biggest practical win is reproducibility. My entire server is defined in .container files sitting in a directory. If this machine dies tomorrow, I can restore everything on new hardware in under an hour. That's not something I could have said about the N100 setup, where the real configuration lived in a tangle of files across /etc and institutional memory in my own head.

There's also something to be said for the forcing function of containers when it comes to good habits. Because each service is isolated, you think harder about what volumes need to be persisted, what ports genuinely need to be exposed, and what each service specifically needs to do its job. Slapping something onto a host machine is easy. Containerizing it correctly makes you understand it.

Is this overkill?

Definitely. A Ryzen AI Max with 128GB of RAM is not a reasonable purchase for hosting a Minecraft server and some media. The N100 comfortably handled everything I needed. But self-hosting has never fundamentally been about the minimum viable solution. It's about learning, experimenting, and building something that's entirely yours.

The Framework Desktop also happens to be my daily driver workstation, so the "server" is pulling double duty. The homelab and the work machine are the same box, which feels appropriately chaotic and somehow very on-brand for how I approach this hobby.

If you're only getting started, please do not take this as a recommendation to spend money on hardware. The $80 thrown-away PC taught me more than I expected. The $200 N100 was more than enough for real use. The upgrade to this machine only made sense because I'd already learned what I concretely needed. Start small. Break things. Fix them. Then decide if you want more.

What's next

Honestly, the stack feels complete for the first time. Not "I ran out of ideas" complete, but "I'm not running services I don't meaningfully use" complete. The AI side has a lot of room to grow, and I'd like to experiment with RAG pipelines over my own documents. There's plenty left to explore on that front.

If anything, this machine has made me lazier in the best way. Things work. Updates happen in a single pull and restart. Backups are predictable because I know exactly what needs to be persisted. The infrastructure fades into the background, which means more time for actively using the services I've set up rather than maintaining them. That's the goal, ultimately. Not to build a complicated system, but to build one complicated enough that you stop thinking about it.
