Relearning Systems Programming Through Rust

July 13th, 2025

Introduction: A Rustacean by accident

I started writing Rust in production because I had to. The opportunity came from the Aurora DSQL project at AWS that demanded low-level performance and hard safety guarantees. The language had already been chosen. At the time, I didn't have much experience with Rust. I have read that it promised memory safety without a garbage collector and seemed to be trending among systems engineers. I expected to wrestle with it, as a lot of programming habits that I have from coding in C will have to be unlearned. What actually happened was that I ended up preferring it to every other language I'd used before.

Rust didn't just solve many memory safety pitfalls in C and C++. It made me think more clearly about ownership, lifetimes, and the shape of my code. It was strict, but fair. And the tradeoffs it enforces led to fewer bugs, more confidence in correctness, and better long-term maintainability.

Compiled vs interpreted languages

Most people outside of software don't think much about how programming languages get turned into something the computer can actually run. There are two broad categories: interpreted and compiled. Interpreted languages like Python and JavaScript are read line by line by an interpreter at runtime. That makes them easy to prototype and debug, but it also makes them slower. In contrast, compiled languages like C, C++, Go, and Rust are translated ahead of time into machine code. The result is a binary, an executable file made of instructions the processor understands directly.

A compiled binary is portable in the sense that it no longer depends on the source code or any interpreter. It's fast, predictable, and efficient, which is why compiled languages are still preferred for systems-level work. What separates Rust from other compiled languages is not performance but safety. The compiler performs a set of checks during the build process that eliminate entire classes of runtime errors. That checking process is sometimes frustrating during development, but the result is a binary you can trust.

Why we use C for systems programming

C is the default choice for performance-critical software. It's used in operating systems, databases, device firmware, and infrastructure tools. Developers keep choosing it because it offers direct access to memory and predictable behavior with very little abstraction. The catch is that with this control comes the responsibility of managing memory manually, allocating and freeing it yourself. That freedom is powerful, but it also creates space for bugs that are often invisible until it's too late. Below is an example of the classic use-after-free memory bug: 

char* message = malloc(100);  // allocate 100 bytes
strcpy(message, "Hello, world!");
free(message);               // release memory
printf("%s\n", message);     // ❌ use-after-free bug

Use-after-free is a good example. In C, if you allocate memory, free it, and then accidentally use it again, your program will do something undefined. Maybe it crashes. Maybe it leaks sensitive data. Maybe it runs just fine and silently corrupts. There is a whole class of memory bugs similar to this one: buffer overflow, double free, memory leak, etc. These bugs are notoriously difficult to detect and reproduce. And they're the source of a significant portion of security vulnerabilities in the wild.

Rust's ownership model: Safety without a garbage collector

Other compiled languages like Go rely on a garbage collector to manage memory. A garbage collector runs in the background and automatically frees memory that is no longer being used. This makes development easier because you don't have to manually release memory or worry about when it gets cleaned up. But the tradeoff is less control over performance. Garbage collection introduces pauses and unpredictable timing, which can be a problem in systems programming, where low latency and determinism are important.

Rust avoids this entire class of problems using its ownership model. Every value has a single owner. When the owner goes out of scope, the value is automatically dropped and its memory is freed. You don't need to call free(). You don't even have access to freed memory, because the compiler prevents it. If you try to use data after it's been moved or dropped, the program won't compile. 

fn main() {
    let message = String::from("Hello, world!");
    println!("{}", message);
} // `message` is automatically dropped here

This is not runtime checking. There is no garbage collector. The checks happen statically at compile time, which means they don't affect performance. The safety comes from the language's rules and the compiler's enforcement of them.

For example, when you assign a value to a new variable, ownership moves:

fn main() {
    let message = String::from("Hello");
    let msg_copy = message; // ownership moves to `msg_copy`
    // println!("{}", message); // ❌ compile error: value borrowed after move
    println!("{}", msg_copy);
}

In this case, message is no longer valid after the move. This may feel strict at first, but it's also what eliminates use-after-free and double free errors entirely.

If you want to use a value without taking ownership, Rust allows borrowing: 

fn print_message(msg: &String) {
    println!("{}", msg);
}

fn main() {
    let message = String::from("Hello, Rust!");
    print_message(&message); // borrow, not move
    println!("{}", message); // ✅ still valid
}

Here, &String is an immutable reference. It allows the function to read message without taking ownership. If you want to mutate the data, you can pass a mutable reference, but Rust ensures that only one mutable reference exists at any given time: 

fn update_message(msg: &mut String) {
    msg.push_str(" is awesome!");
}

fn main() {
    let mut message = String::from("Rust");
    update_message(&mut message);
    println!("{}", message); // ✅ "Rust is awesome!"
}

This borrow checker is one of Rust's most powerful tools. It forces you to be explicit about who owns what, when, and for how long, and it catches violations at compile time. That combination allows Rust to offer both memory safety and the low-level control typically associated with unsafe languages like C.

Will Rust replace C?

In some places, yes. In many others, not yet. There are caveats. Rust binaries tend to be larger than C binaries. This matters in embedded systems where you might only have a few hundred kilobytes of flash storage to work with. In those cases, the extra overhead from Rust's runtime support and static linking can make it a bad fit. C is also deeply entrenched in legacy codebases, toolchains, and developer ecosystems that have been in place for decades. Rewriting everything in Rust is not practical, nor is it necessary.

What Rust offers is a better starting point for new software. If you are building something today and you care about correctness, reliability, and performance, then Rust is worth serious consideration. It's already gaining ground in domains where safety matters such as cryptography, networking, and systems infrastructure. AWS, Google, Microsoft, and even the Linux kernel are writing new components in Rust. That momentum is not accidental.

Conclusion: The right tool at the right level

Rust won't eliminate C, and it doesn't need to. What it does is raise the baseline. It shows that we no longer have to choose between safety and performance. We can write code that is fast, expressive, and correct, without relying on runtime garbage collection or manually managing memory. That's not a small thing.

For me, Rust didn't just solve technical problems, but it also changed how I think about writing code. It made things that used to be difficult feel solid and predictable. It's the first language I've used that feels both powerful and principled. I didn't expect to enjoy it. But I do.

And I'm not the only one.
